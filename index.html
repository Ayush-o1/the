Mission 01 / Argus

Argus

Complete

Objective

Argus is a graph investigation tool over a made-up world. It has 70 real cities in 50 countries and no real people. An analyst follows links between people, accounts and shipments, runs graph algorithms and opens cases.

What it does

  • Runs PageRank, community detection and cycle detection on the graph in Neo4j.
  • Raises alerts from named, versioned rules and keeps an append-only audit log that a command can re-check.
  • Lands every imported record untouched first. Rejected records go to a dead-letter queue with a reason.

Hazards met

  1. Hidden patterns. The anomaly detector flags an account only when an Isolation Forest and a z-score of 3 or more both agree. It never reads the generator's answer key.
  2. Marking its own homework. Precision and recall are published against ground truth the detectors never saw. Planted cases it cannot detect are listed with a recall of 0 and the reason.
  3. Silent data loss. A silent drop makes a gap look like a quiet world. So nothing is dropped without a trace.

Simulation

Simulation. Synthetic data. Not the live app.

In the real run, a planted burst of 35 transactions inside six hours scored a z-score of about 37. The rule is simple: an account is flagged when its burst count sits 3 or more standard deviations above the rest and the Isolation Forest also calls it an outlier.

Flight recorder
  • Decision. Transactions are edge properties, not nodes. An account to account link is the money graph, so the algorithms run on it directly.
  • Decision. Neo4j holds the graph. PostgreSQL holds identity, the audit log and the job queue, which uses FOR UPDATE SKIP LOCKED. A restart postpones a batch instead of losing it.
  • Decision. No hosted AI service. Entity narratives are composed from templates. A local model assistant exists and nothing depends on it.
  • Trade-off. One instance, one tenant. Rate limiting is per process.
  • Python
  • FastAPI
  • Neo4j
  • PostgreSQL
  • Redis

Mission 02 / BlackWater

BlackWater

Active

Objective

BlackWater is incident management with a public status page. A team lists its services, declares an incident when one breaks and works it through a fixed lifecycle. It also decides which incidents customers get to see.

What it does

  • Moves an incident through TRIGGERED, ACKNOWLEDGED, RESOLVED and CLOSED. A closed incident is final.
  • Works out each service's health from its open incidents. Nobody types it in.
  • Shows visitors only the incidents a team has published, and refreshes open pages over Socket.IO.

Hazards met

  1. Two people, one incident. Every change locks the incident row, checks the lifecycle table and writes its audit entry in one transaction.
  2. Health that disagrees with the incidents. Health is never stored. It is calculated each time it is read, and the worst open incident wins.
  3. A private incident on a public page. The public page reads an allow-list of fields and only published incidents. Every query is filtered by organization.

Simulation

Simulation. Synthetic data. Not the live app.

Flight recorder
  • Decision. The lifecycle is a lookup table checked inside the transaction, after the row lock. Two requests cannot both pass the same check.
  • Decision. Live updates are a doorbell. The server says "incident X changed" to the organization's room and each page refetches through the normal API.
  • Decision. The interface is plain HTML, CSS and JavaScript served by the same Express app. No framework, no build step.
  • Trade-off. One instance only, because rooms and rate limits live in process memory. No password reset and no email.

Mission 03 / BeetleJuice

BeetleJuice

Active

Objective

A merchant records payments. Its processor reports what it settled. The two rarely agree. BeetleJuice compares the two exports, explains every difference and sends each exception through maker-checker approval. It uses synthetic data only.

What it does

  • Checks both CSV exports strictly and lists every rejected row with its reason.
  • Applies its rules in a fixed order, so every record ends with exactly one explained outcome.
  • Lets an analyst propose a fix. A different supervisor approves or rejects it.

Hazards met

  1. A reference that is not unique. A payment and its refund can share one. When both sides have leftovers that do not line up, every record involved becomes AMBIGUOUS_REFERENCE. Nothing is paired by guesswork.
  2. Late is not missing. A settlement window and an as-of date decide. Results never change in place. A later run looks again.
  3. Approving your own fix. The service refuses it, and database triggers refuse it again.

Simulation

Simulation. Synthetic data. Not the live app.

Example from the rules: the ledger says ₹1,200.00 and the settlement says ₹1,250.00. The outcome is AMOUNT_MISMATCH with a difference of +₹50.00. The analyst who proposes the fix cannot approve it. A different supervisor has to.

Flight recorder
  • Decision. Money is whole paise everywhere. Fees are exact fractions with one documented half-up rounding rule.
  • Decision. The database enforces the invariants too: one result per record per run, one pending proposal per break, and no self-approval.
  • Decision. Plain SQL, no ORM. The matching engine is a pure function, so the same inputs always give the same output.
  • Trade-off. No bank-holiday calendar. The settlement window counts calendar days.
  • Node.js
  • Express
  • PostgreSQL
  • Plain SQL

Mission 04 / theRedArmy

theRedArmy

Active Team project

Objective

theRedArmy tests LLM prompts the way you test code. Write the test cases once, run every new prompt version against them and see which cases broke. A CI pipeline can call it and fail the build.

What it does

  • Saves prompts as immutable versions and runs each one against a test suite.
  • Turns a run into one job per test case in a PostgreSQL queue, worked by separate worker processes.
  • Gates a CI build. With a baseline, a case that already failed is tolerated and a case that used to pass and now fails stops the build.

Hazards met

  1. Two workers, one job. Jobs are claimed with FOR UPDATE SKIP LOCKED and leased. A late write from a dead worker is rejected.
  2. Rate limits and flaky calls. A shared Redis token bucket limits each provider. Transient errors retry with backoff and jitter. Permanent errors do not.
  3. Silent regressions. A run is compared with its baseline, case by case: regressed, fixed, still failing, added or removed.

Simulation

Simulation. Synthetic data. Not the live app.

The seeded demo has a support-reply prompt. Version 1 quotes the order number and passes all 8 cases. Version 2 was shortened to save tokens and dropped the order number. Seven cases regress and one still passes, so the gate fails.

Flight recorder
  • Decision. The run_cases table is the queue. Starting a run inserts the run and its jobs in one transaction.
  • Decision. Only deterministic checks, such as contains, regex, is_json and length. A model judging a model would be slow, paid and different each time.
  • Trade-off. The built-in provider echoes the prompt back. It exercises the pipeline for free and cannot say whether a real prompt is good.
  • Team. This was built with others. The contributors page lists everyone.
  • Node.js
  • Express
  • PostgreSQL
  • Prisma
  • Redis

Mission 05 / deadLetter

deadLetter

Active

Objective

deadLetter is a firewall between an AI agent and its tools. The agent may read untrusted text, such as an email, but that text cannot choose which tool runs or where private data goes. It is a local prototype with fake tools, built on the CaMeL design from a research paper.

What it does

  • Splits the agent in parts: a planner that sees only your request, a model with no tools that reads untrusted text, and an interpreter that tracks where every value came from.
  • Checks every tool call against those labels and answers allow, ask or deny.
  • Runs 20 prepared scenarios, 11 attacks and 9 normal tasks, against three defences.

Hazards met

  1. Prompt injection. It does not guess whether text is malicious. It asks where a value came from and whether that source may drive this action.
  2. Private data leaving. If untrusted text picks the destination and private data goes with it, the call is denied. Nobody can override a deny.
  3. Grading itself kindly. The results use mock models and say so. One attack still gets through, a misleading summary sent to an allowed recipient, and the project lists it.

Simulation

Simulation. Synthetic data. Not the live app.

Flight recorder
  • Decision. Plans are JSON checked by a strict schema. Nothing is evaluated as code.
  • Decision. Labels can only get more restrictive when values combine. A second implementation, written separately, is checked against the real one on random graphs.
  • Decision. A tool runs only with a single-use token bound to the exact call. The audit record is written before the action.
  • Trade-off. Human approval can be mistaken, and the tools are fakes. It does not show that a real mailbox integration would be safe.

Mission 06 / Europa

Europa

Complete

Objective

Europa is a workbench for satellite close approaches. It reads public conjunction reports, tracks how each predicted miss distance changes between updates, ranks what to review first and keeps every review action in a hash-chained log.

What it does

  • Recognises the same pair of satellites across reports, even when the order of the two swaps.
  • Scores review priority from 0 to 100 from miss distance, time to closest approach, a probability bound and the age of the data.
  • Records each review action with a required reason. Every entry holds the hash of the one before it.

Hazards met

  1. Same pair, different order. A pair gets one key built from the smaller and larger catalog number, so A against B and B against A are one event.
  2. Reports are snapshots. Predictions are matched over time. A miss distance that shrinks by 20% or more flags the event for another review.
  3. Tampered records. Database triggers block updates and deletes on the log. A verifier walks the chain from the first entry to the last.

Simulation

Simulation. Synthetic data. Not the live app.

Each log entry is hashed with SHA-256 over its sequence number, action, actor, payload, the previous hash and the time. Change any field in an old entry and its hash no longer matches. So does every entry after it.

Flight recorder
  • Decision. The priority score is a review heuristic and not a collision probability. The project says so in its README.
  • Decision. Appends are serialised with a database advisory lock, so two writers cannot both extend the same chain head.
  • Trade-off. A database administrator could still rewrite the whole chain. Catching that needs the head hash stored somewhere else.
